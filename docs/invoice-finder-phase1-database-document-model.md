# Invoice Finder — Phase 1: Database and document model

Source: `feature/android-v1-complete`. Work branch: `feature/invoice-finder-document-model`.

## Scope implemented

- Room database **v6 → v7**, via a non-destructive `MIGRATION_6_7`.
- `purchase_invoices`: multiple **approved** local invoice documents per purchase order.
- `invoice_candidates`: mailbox attachment discovery/review metadata (without saving PDF files).
- `email_accounts`: connected mailbox metadata only; OAuth secrets are intentionally not stored in unencrypted Room tables.
- Purchase-level `invoiceSequence` and `invoiceSupplierKey` fields for stable, date/supplier-specific Dropbox filenames.
- Legacy `purchase_orders.invoicePath` (or first qualifying legacy `purchases.invoicePath`) references backfilled as an approved invoice. Existing physical files are not moved, renamed, or deleted by migration.
- The existing Purchase editor still uses the legacy single-file slot; saves/replacements also populate the new table.
- Repository APIs: `attachAdditionalPurchaseInvoice`, `getPurchaseInvoiceDocuments`, `removePurchaseInvoiceDocument`.
- SHA-256/size capture for new attachments, duplicate-detection per order, unique per-order invoice ordinal.
- Deleting a purchase also cleans up its new invoice paths. Database document/candidate rows are deleted by FK cascade.
- Removed destructive migration fallback: an unsupported migration fails safely instead of deleting purchasing records.

## Tables and links

```
purchase_orders (1) ─── (*) purchase_invoices
      │
      └─────────────── (*) invoice_candidates

email_accounts  (mailbox configuration; no OAuth credentials)
```

`purchase_invoices` represents **approved** attachments only. `invoice_candidates` represents **unapproved/rejected email findings** only. An approval operation will be introduced with the Finder workflow; it must explicitly associate one candidate with an approved document, and no email search should run for an order if one or more approved invoices already exist.

## Exact-account matching rule for the next stage

Only search if `purchase_orders.orderNumber` and `purchase_orders.accountUsername` both contain usable values and the username is an exact normalised email address of an actively connected mailbox. Search **that mailbox only**. Never fall back to searching another connected account. General Invoice Finder runs skip orders with one or more approved invoices. Users may add additional invoices manually irrespective of email status.

## Filename convention

Store invoice sequence **on the order**, not calculated from current list positions. The intended exported Dropbox filename is generated by `InvoiceDocumentNaming`, for example:

- `14 Oct 2026 - Costco #1.pdf`
- `14 Oct 2026 - Costco #2.pdf`
- Second invoice on the second purchase: `14 Oct 2026 - Costco #2 - Invoice 2.pdf`

Keep database invoice IDs and original filenames independently from the display/export filename. Preserve the existing accounting-period folder hierarchy. File renaming/Dropbox multi-invoice upload is a **later phase**; **it is not implemented here**.

## Current compatibility and limits

The pre-existing `invoicePath` column remains for the current purchase editor, Dropbox sync, and document exporter. New additional documents are stored in `purchase_invoices`, but **will not yet be visible in the current app UI or automatically synced/exported to Dropbox**. The later Dropbox/export integration must iterate `purchase_invoices` and avoid duplicating the legacy slot.

The current file-per-order slot can still be replaced using the existing purchase editor. That changes only its associated approved invoice row, preserving any additional documents.

## Safety/verification checklist

1. Back up the phone's current app data and Dropbox content before upgrading.
2. Open an existing v6 installation and verify all historic purchase orders, invoice references, sales, refunds, and credit notes remain intact after v7 migration.
3. Verify each old order invoice is represented exactly once in `purchase_invoices`, with original paths still readable.
4. Verify blank invoice orders produce no document rows.
5. Verify two purchases on the same day and for the same supplier receive distinct, stable sequence numbers; a different day or supplier starts again at 1.
6. Verify two manual attachments to one order have distinct ordinals; reattaching identical bytes is rejected.
7. Verify deleting one document does not remove other documents on the same order, and deleting an order cascades its document/candidate rows.
8. Verify current purchase editing and the existing Dropbox single-invoice behaviour are unchanged.
